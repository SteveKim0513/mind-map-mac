# 보드 자동 정렬 재설계 + 화살표 연결 디자인 개선

날짜: 2026-09-07
상태: completed

## 목표

"자동 정렬이 별로다", "화살표 연결 디자인이 별로다"라는 피드백을 받아 외부 툴(Miro,
FigJam, tldraw)을 벤치마크하고, 이 코드베이스에 이미 있는 자산(마인드맵의 검증된
레이아웃 알고리즘, 이미 선언된 라이브러리)을 최대한 재사용해 근본적으로 개선한다.

## 조사 결과 요약

### 자동 정렬 ("정리" 버튼)

**현재 구현**(`board/boardLayout.ts`의 `autoLayoutPositions`): 선택한 루트에서
BFS로 연결된 자손을 찾아 **깊이(depth)별로 항상 오른쪽 열**에 배치하고, 같은 열의
형제는 높이를 단순히 합산해 세로로 쌓기만 한다.

**구체적 결함**:
1. 보드는 스티키를 4방향(상하좌우) 화살표로 자유롭게 연결하도록 설계돼 있는데(방향키로
   자식 생성), "정리"는 그 방향 정보를 완전히 무시하고 **항상 오른쪽으로만** 재배치한다.
   아래쪽으로 구조를 만든 사용자가 "정리"를 누르면 자신이 만든 방향과 다른 결과가 나옴.
2. 형제 간격이 "높이 합산 + 고정 간격"뿐이라 트리가 깊어지거나 크기가 다양하면 성기게
   벌어지거나 불필요하게 넓어짐 — 제대로 된 압축(compaction)이 없음.
3. 다중 부모(다이아몬드 구조)는 "첫 경로만 인정, 이후 무시"로 조용히 무너짐.

**벤치마크**: Miro의 "Layout nodes"(마인드맵 정리 기능)는 기존 구조를 **존중하며
가지런히**(tidy) 만드는 것에 가깝다 — 완전히 새 구조를 강제하지 않는다. 이게 사용자가
"정리"에 기대하는 감각에 더 가까울 것으로 보인다.

**결정적 발견**: 이 프로젝트의 마인드맵(`layout/treeLayout.ts`)이 이미 훨씬 정교한
"block-packing" 레이아웃 알고리즘을 갖고 있다 — 각 서브트리가 자신의 세로 대역을
예약해 형제끼리 절대 안 겹치고, 노드 크기(칩·배지 포함 실측 크기)에 맞춰 정확히
압축된다. **board는 도메인 경계상 `layout/`의 내부 함수를 직접 import할 수 없지만
(같은 이유로 `boardLinks.ts`가 `note/noteLinks.ts`를 복제한 전례가 이미 있음),
같은 알고리즘 패턴을 board 전용으로 새로 구현**하면 검증된 품질을 가져올 수 있다.
추가로 부록으로 발견: `package.json`에 `d3-hierarchy`가 선언돼 있지만(`AGENTS.md`의
저장소 지도에도 "d3-hierarchy"라고 적혀 있음) **실제로는 `src/` 어디에서도 import되지
않는 죽은 의존성**이다(마인드맵도 손수 짠 block-packing을 쓰지, d3-hierarchy의
`tree()`를 쓰지 않음) — board 레이아웃도 이걸 쓸 필요 없다(칩 포함 실측 크기 배치는
d3-hierarchy의 기본 tree()가 잘 못 다루는 영역이라, 어차피 손수 구현이 더 낫다).
**새 의존성 없이, 기존 검증된 알고리즘 패턴만 재사용하는 게 최선의 경로.**

**제안하는 재설계**:
- 각 자식을 부모와 실제로 연결된 **화살표의 앵커 방향**대로 배치(아래로 연결했으면
  아래, 오른쪽이면 오른쪽 — 사용자가 만든 공간적 의도를 존중).
- 같은 방향의 형제들은 `treeLayout.ts`와 같은 **서브트리 대역 예약 방식**으로 압축
  배치(높이 합산 대신 실제 겹침 없는 최소 공간).
- 다중 부모/사이클은 기존처럼 "첫 방문만 인정"으로 안전하게 처리(변경 없음).
- 루트 자신의 위치는 그대로 유지(기존 동작과 동일).

### 화살표 연결 디자인

**현재 구현**: 직각 기반(orthogonal) 라우팅 + 모서리 둥글림(`boardRouting.ts`) — 이미
Miro/FigJam/Whimsical, 그리고 tldraw가 최근 추가한 "elbow arrows"와 **같은 업계
표준 패턴**이다(tldraw 팀 코멘트: 완전 곡선형 화살표는 자동 라우팅 시 예측 불가능하고
지저분해지기 쉬워 신중했다고 함). 즉 **알고리즘 자체는 최신 트렌드와 정확히 일치** —
"별로"인 지점은 시각적 디테일/기능 쪽일 가능성이 높다.

**구체적 결함(객관적, 바로 고칠 수 있음)**:
1. 화살촉(`<marker id="board-arrow">`)이 `fill="var(--ink-muted)"`로 **하드코딩**돼
   있다 — 커넥터를 선택(`.selected`)하거나 hover해서 선 색이 primary/ink로 바뀌어도
   **화살촉만 회색 그대로** 남는다. 눈에 띄는 불일치.
2. 스티키는 전체 태그 팔레트로 색을 바꿀 수 있는데, **커넥터는 색을 전혀 지정할 수
   없다**(지난 라운드 감사에서도 확인된 공백) — Miro/FigJam/Whimsical 모두 커넥터
   색상 커스터마이즈를 기본 제공한다.

**제안**:
- 화살촉 색을 선의 상태(기본/hover/selected)와 항상 일치시킨다(마커를 상태별로
  나누거나 `context-stroke` 활용).
- 커넥터에 `color` 필드 추가(스티키와 동일한 태그 팔레트) — 선택 시 플로팅 메뉴에서
  색 변경, 화살촉·선 모두 그 색을 따름.

## 위험

- `autoLayoutPositions` 재작성은 기존 유닛 테스트(`boardLayout.test.ts`)의 좌표
  기대값이 크게 바뀐다 — 새 알고리즘 기준으로 다시 작성 필요.
- 방향 인식 레이아웃은 한 부모가 4방향 모두에 자식을 가질 수 있어, 각 방향별로
  독립적인 서브트리 대역 계산이 필요(코드 복잡도 증가) — 테스트로 각 방향 케이스를
  반드시 커버.
- 커넥터 `color` 필드 추가는 `types.ts`(BoardConnectorElement)·`boardStore.ts`
  (`BoardElementPatch`)·직렬화 스키마 확장이라 작지만 문서 스키마 변경에 해당 —
  `BoardDoc.version`은 그대로 두고(선택 필드 추가는 기존 관례상 무범프 허용,
  ADR 0012 선례) 하위 호환 유지.

## 검증 방법

- 유닛: 4방향 각각으로 자식을 만든 뒤 "정리" 결과가 그 방향에 배치되는지, 같은 방향
  형제들이 겹치지 않고 압축되는지.
- E2E: 아래쪽으로 트리를 만들고 "정리"를 눌러 결과가 실제로 아래쪽에 남는지(회귀
  방지 — 오른쪽으로 튀지 않는지), 커넥터 색 변경 후 화살촉·선 색이 일치하는지.
- `make dev-safe`로 실제 앱에서 라이트/다크 모두 육안 확인.

## 발견한 사실 (작업 중 갱신)
- `d3-hierarchy`가 `package.json`에 선언돼 있지만 `src/` 어디에서도 쓰이지 않는
  죽은 의존성임을 발견(별도 정리 대상, 이번 작업 범위 밖 — 사용자 승인 필요한
  의존성 변경이라 언급만 남김).
- `BoardConnectorElement.color`는 이미 필드도 있었고 라인 렌더링(`tagVar(el.color)`)도
  이미 그 값을 읽고 있었다 — 정말로 빠져 있던 건 "설정할 UI" 하나뿐이었다. 코드를
  훑기 전엔 "전체 기능이 없다"고 짐작했지만, 실제로는 데이터 모델·렌더링은 완성돼
  있고 마지막 한 조각(진입점)만 빠진 상태였다.
- 방향 인식 재작성이 기존 rightward-only 유닛 테스트 11개를 **전혀 수정하지 않고도**
  그대로 통과했다 — 새 알고리즘이 `fromAnchor:'right'` 케이스에서 이전 알고리즘과
  수학적으로 동일한 결과를 내도록 설계했기 때문(같은 상수 `PRIMARY_GAP`/`CROSS_GAP`,
  같은 중심 정렬 방식). 회귀 없이 순수 확장임을 강하게 뒷받침.
- hover 강조가 `stroke` 자체를 덮어써 커스텀 색을 지우던 문제는 커넥터 색 기능을
  만드는 과정에서 실사용 스크린샷으로 우연히 발견 — 유닛 테스트만으로는 못 잡는
  종류(시각적 상호작용 조합)라 `make dev-safe`급 실사용 확인이 여전히 필요함을
  재확인.
