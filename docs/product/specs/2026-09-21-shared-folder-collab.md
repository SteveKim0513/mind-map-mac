## 1. 문제 (Why)

혼자 쓰는 로컬 파일 기반 마인드맵/노트 앱에서, 여러 사람이 초대 코드로 폴더를 공유하고
협업할 방법이 없다. 사용자가 원하는 모델은 명확하다.

- 폴더 소유자가 공유 폴더를 만들면 초대 코드가 생성되고, 다른 사용자는 코드로 참가한다.
- **노트(텍스트 문서)는 여러 명이 실시간으로 동시 편집**할 수 있어야 한다.
- **마인드맵/보드(캔버스류)는 소유자만 편집**하고, 나머지 참가자는 **보기 + 코멘트**만 가능하다.

## 2. 벤치마킹 — 다른 서비스는 어떻게 하는가

| 서비스 | 모델 | 인프라 | 이 프로젝트에 주는 시사점 |
|---|---|---|---|
| **Google Docs** | OT(Operational Transform), 서버가 모든 편집의 단일 진실 소스 | 완전 중앙 서버, 오프라인 시 로컬 큐 후 재적용 | 서버가 콘텐츠를 항상 갖고 있어야 함 — "서버 없음" 철학과 정반대. 참고만, 채택 안 함. |
| **Figma** | 자체 개발 CRDT(멀티플레이어 서버) | 완전 중앙 서버, 오프라인 미지원 | "로컬 우선"을 포기한 대가로 매끄러운 동시편집을 얻음. 캔버스 코멘트는 요소에 핀으로 고정 — 이 앱의 보드 코멘트 모델로 그대로 참고할 만함. |
| **Notion** | 블록 단위 op 동기화, 서버 권위(authoritative) | 완전 중앙 서버 | 뷰/코멘트/편집 3단계 권한 체계가 이 프로젝트가 원하는 것과 정확히 일치. 권한 UX 참고. |
| **Obsidian Sync** | 실시간 동시편집 **없음** — 파일 단위 종단간 암호화 동기화 + 버전 히스토리, 충돌 시 두 버전 모두 보존 | 자체 유료 릴레이 서버, 서버는 암호화된 blob만 중계(내용을 못 읽음) | **이 프로젝트와 철학이 가장 가깝다.** "파일이 원본"을 지키면서 서버는 그저 중계자. 다만 진짜 동시편집은 지원 안 함 — 사용자가 원하는 "노트 동시편집" 요구와는 이 지점에서 갈린다. |
| **tldraw (캔버스)** | 자체 CRDT 기반 sync 엔진, 이전엔 Yjs 사용 | 자체 서버(엣지 배포) | 캔버스형 협업도 CRDT로 가능함을 보여주지만, 이 프로젝트는 캔버스를 굳이 동시편집으로 만들 필요가 없다(사용자 요구사항도 소유자 전용 편집). |
| **Liveblocks / PartyKit** | CRDT-as-a-Service (관리형) | **제3자 클라우드** | 구현은 가장 빠르지만 사용자 문서 내용이 우리가 아닌 제3자 회사 서버를 거친다 — "서버로 전송 안 함" 원칙 위반 폭이 가장 크다. 제외 권장. |
| **Yjs + Hocuspocus** | CRDT 라이브러리(Yjs) + Tiptap 팀이 만든 자체 호스팅 WebSocket 백엔드(Hocuspocus) | **자체 호스팅**(우리가 서버를 직접 운영) | 지금 에디터가 이미 Tiptap이라 통합 경로가 가장 잘 닦여 있음. 서버를 직접 운영하므로 "제3자에게 전송"은 피할 수 있고, 인증/영속화 훅을 우리가 통제할 수 있어 "서버는 중계만, 콘텐츠는 영속 저장 안 함" 정책을 기술적으로 구현 가능. **추천.** |

**결론**: Obsidian Sync의 철학(서버는 콘텐츠를 못 읽는 중계자, 파일이 원본)과 Figma/Notion의
UX 패턴(권한 3단계, 캔버스 요소에 코멘트 핀 고정)을 가져오되, 실제 동시편집 엔진은
Google Docs식 OT가 아니라 **Yjs CRDT**로 구현한다. 이유: OT는 서버가 편집 순서를 중재해야
하는 중앙집중 모델이라 "서버가 콘텐츠를 모른다"를 지키기 어렵고, CRDT는 두 클라이언트가
직접 병합 가능한 연산을 만들기 때문에 서버는 진짜로 "바이트를 중계"하는 역할에 더 가깝게
남을 수 있다.

## 3. 우리 시스템 현황 (조사 결과 요약)

- 노트 에디터: Tiptap 3.26 (`src/note/NoteEditor.tsx`). 현재는 **타이핑마다** ProseMirror
  문서를 마크다운 문자열로 즉시 변환해 부모에 전달하는 구조(`onUpdate` 콜백) — 마크다운
  문자열 자체를 진실로 취급한다. 동시편집을 붙이려면 "진실"이 마크다운 문자열에서 **Yjs
  문서(Y.Doc)**로 이동해야 하고, 마크다운 변환은 저장 시점(디바운스)으로 옮겨야 한다.
  이건 부가 기능이 아니라 노트 에디터 파이프라인의 구조 변경이다.
- 노트 파일 포맷(`src/io/noteFormat.ts`): 프론트매터가 JSON 인코딩이라 `shareId`/
  `collabRoomId` 같은 새 필드를 추가하는 건 자연스럽다.
- 기존 동기화 도메인(`src/sync/`, Reminders): "로컬은 이벤트 즉시 push + 외부는 폴링"
  하이브리드, 필드 단위 content-diff 충돌 해소. 이건 **1:1 매핑(로컬 문서 ↔ Reminders)**
  모델이라 **N인 동시편집**에는 재사용하기 어렵다. 다만 health/backoff 상태기계(연결 끊김
  → 지수 백오프)는 WebSocket 연결 관리에 그대로 참고할 만하다.
- 보드(`src/board/`, ADR 0020): 캔버스와 완전히 분리된 독립 도메인, 절대좌표 자유배치.
  스티키가 `nodeLink`/`noteLink`로 마인드맵 노드·노트를 참조하는 기존 패턴이 있어, **코멘트
  앵커도 화면 좌표가 아니라 노드/요소 id에 고정**하면 다른 사람이 레이아웃을 바꿔도 안
  깨진다.
- 노드 ID·문서 ID 불변성(`MindNode.id`, `MindMapDoc.id`, `BoardDoc.id`)이 이미 "생성 후
  불변"이라, 공유 참가자 간 참조·코멘트 앵커·diff 기준점으로 그대로 쓸 수 있다.
- 아키텍처 경계상 새 도메인은 `src/share/`로 신설하고 다른 도메인(note/canvas/board)과는
  store를 통해서만 연결해야 한다(`.claude/rules/architecture.md`). 새 IPC 채널은
  `share:*` 네이밍으로 `preload.ts` → `main.ts` 순으로 추가.

## 4. 해결 (What) — 추천 아키텍처

### 4.1 서버 역할: "중계 전용, 영속 저장 없음"

- **자체 호스팅 WebSocket 서버**(제3자 서비스 아님)를 하나 새로 운영한다. 역할은 딱 둘:
  (1) 초대 코드 발급·검증·참가자 연결 중개, (2) 연결된 클라이언트 간 실시간 메시지 릴레이.
- 서버는 문서 내용을 **디스크에 영구 저장하지 않는다** — 접속 중인 클라이언트가 없어지면
  메모리 버퍼도 비운다(재접속 시 마지막 클라이언트가 갖고 있던 최신 상태를 다시 브로드캐스트).
  이게 Obsidian Sync식 "서버는 중계자, 파일이 원본"을 기술적으로 지키는 핵심 장치다.
  → 구현: `server/`(Hocuspocus + REST 한 포트, `startRelay()`). 방(room) = 공유 폴더 하나, 문서 이름
  `${roomId}/${docKey}`(`manifest` · `note:<noteId>` · `file:<fileId>` · `comments`). 운영: [relay-server.md](../../operations/relay-server.md).
- 이 정책은 ADR로 명문화해야 한다: "서버 없음" 불변 조건을 "사용자 파일은 로컬이 원본이며,
  공유 모드에서만 자체 호스팅 릴레이를 거친다. 릴레이는 콘텐츠를 영속 저장하지 않는다"로
  재정의하는 제안.

### 4.2 노트 — 실시간 동시편집

- **Yjs + Hocuspocus + `@tiptap/extension-collaboration`** 조합. Tiptap 팀이 만든 조합이라
  통합 리스크가 낮다.
- `NoteEditor.tsx`의 "타이핑마다 마크다운 변환" 파이프라인을 "Y.Doc이 진실, 마크다운은
  저장 시점에만 파생"으로 재구조화해야 한다(위 3절).
- Yjs의 **awareness 프로토콜**로 커서 위치·참가자 아바타를 표시(누가 어디를 편집 중인지
  1초 안에 보여야 한다는 `UI-DESIGN-PRINCIPLES.md`의 상태 가시성 원칙과 일치).
- 오프라인 편집 정책: 온라인 상태에서는 진짜 동시편집, 오프라인에서 로컬 편집 후 재접속하면
  Yjs가 자동 병합한다(CRDT의 핵심 이점 — 수동 충돌 해결 UI가 필요 없다).
  단, 서버가 상태를 폐기하므로 **각 클라이언트가 Y.Doc 상태를 숨김 사이드카로 로컬에 보존**해야 하고,
  같은 `.md`에서 각자 시드하면 내용이 중복되는 문제는 착수 전 스파이크로 검증한다(ADR 0021, exec-plan 단계 2).
  → 구현: 사이드카는 `.{stem}.yjs`가 아니라 **공유 폴더 안 숨김 디렉터리 `.mindshare/<noteId>.yjs`**(노트 id 기반 이름 —
  제목 변경 rename에 끌려가지 않는다). 같은 디렉터리의 **`.mindshare/room.json`이 공유 폴더 표식**(`roomId`·`relayUrl`·
  `role`·`participantId`·`folderName`·`displayName`)이고 토큰은 파일이 아니라 `safeStorage`에 둔다. 시드는 소유자가
  노트당 1회, 참가자는 원격 상태를 채택(중복 방지 규칙은 exec-plan "스파이크 결과"). 각 참가자는 공유 폴더의 모든
  노트를 항상 로컬에 복제한다(eager replica, 300개 상한 — 초과분은 열 때 받음).
  이미지는 v1 제외(공유 노트에는 삽입 차단).
- 서버가 영속 저장하는 것은 콘텐츠가 아니라 **메타데이터**(방 id, 참가자 토큰 해시, 표시 이름,
  강퇴 목록)뿐이다 — 재시작해도 참가 관계가 유지되려면 필요하다.
  → 구현: 여기에 **폴더 이름(`folderName`, 표시용)**이 더해졌다 — 참가 응답(`/join`)이 폴더 이름을 돌려줘 참가자
  워크스페이스에 같은 이름의 폴더를 만들 수 있다. 초대 코드는 sha256 해시만 저장한다.

### 4.3 마인드맵 / 보드 — 소유자 전용 편집 + 뷰 + 코멘트

- CRDT 불필요. 소유자 클라이언트가 권위 있는 쓰기 주체이고, 서버는 "파일이 바뀌었다"는
  이벤트만 참가자들에게 릴레이한다 — 이미 있는 `fs:externalChange`(외부 변경 감지→새로고침)
  패턴을 원격 버전으로 확장하는 느낌이라 새 개념을 만들 필요가 적다.
  → 구현: 이벤트만이 아니라 **소유자가 저장할 때마다 파일 내용(스냅샷)을 `file:<fileId>` 문서(Y.Map: content·rev·kind)로
  발행**하고 참가자가 읽기 전용 미러 파일로 받는다(서버는 비소유자의 `file:*` 쓰기를 readOnly로 강제). 참가자 화면은
  포커스 없이 실시간 반영되고 `store/readOnlyGuard`가 모든 편집·저장을 막는다. 발행·수신 사본에서 리마인더 4개 필드를
  제거한다. 참가자가 공유 폴더 안에 직접 만든 맵·보드는 로컬 전용이다. 파일 하나 4MB(4×1024×1024자)·동시 300개 상한.
- **코멘트**: 마인드맵은 `nodeId`, 보드는 요소 `id`에 고정된 스레드(작성자·시각·본문)로
  추가한다. Figma 스타일 핀 UI. 별도 append-only 로그라 CRDT 없이 "추가만" 이벤트로 동기화
  가능(last-write-wins조차 필요 없음 — 코멘트는 삭제/수정이 드물고, 삭제는 작성자 소유
  검증만 하면 됨).
  → 구현: 핀 UI가 아니라 **"코멘트 N개" 칩 + 스레드 팝오버**(진입점: 노드·요소 우클릭 "코멘트 남기기", 노트 헤더 "코멘트" 버튼).
  코멘트는 `comments` 문서(`Y.Map<commentId, Comment>`)에 살고 로컬 사이드카에 보존된다. **노트 코멘트는 노트 전체
  단위**(텍스트 범위 앵커 없음). 답글 지원, 삭제는 soft delete("삭제된 코멘트예요"). 본문 2000자·방당 5000개 상한.
  **작성자 검증은 서버가 하지 못한다**(`comments`는 모두 쓰기 가능한 문서) — "내 코멘트만 삭제"는 UI 규칙일 뿐이다.
- **코멘트 즉시 알림**: 코멘트가 생성되면 같은 WebSocket 채널로 관련자(그 파일의 소유자 +
  같은 코멘트 스레드 참여자)에게 **즉시 브로드캐스트**된다. 수신자가 앱을 열어 두고 있으면
  토스트 + 해당 노드/요소 위치에 뱃지가 지연 없이 뜬다(폴링 아님 — Reminders 동기화의
  45초 폴링과 달리, 코멘트는 이미 상시 연결된 소켓이 있으므로 push로 바로 전달 가능).
  다른 파일/탭을 보고 있어도 사이드바나 탭에 읽지 않은 코멘트 뱃지가 즉시 반영된다.
  → 구현: 알림은 별도 서버 채널이 아니라 **`comments` 문서 관찰로 클라이언트가 로컬에서 만든다**(폴링 없음). **알림 대상 규칙**:
  방 소유자는 모든 새 코멘트, 참가자는 자기가 참여한 스레드(같은 노드·요소·노트에 이미 코멘트했거나 내 코멘트에 달린 답글)만.
  내가 쓴 코멘트·삭제된 코멘트는 알림이 아니다. 새 기기는 기준선(참가 시각, 60초 여유) 이전 코멘트로 알림을 만들지 않는다.
  탭 뱃지는 만들지 않았고 사이드바 종 버튼 뱃지 + 즉시 토스트("보기")로 알린다.
- 뷰어는 같은 WebSocket 채널의 awareness로 "지금 보고 있는 사람" 표시(편집 권한이 없어도
  프레즌스는 보여줘야 "왜 코멘트만 되지?"가 아니라 "이건 원래 보기 전용"임이 자명해짐 —
  Simple·Powerful·Intuitive 원칙).
  → 구현: **맵·보드의 뷰어 프레즌스는 범위에서 제외**했다(§5). 대신 참가자에게는 상단 **"보기 전용 · 소유자만 편집할 수 있어요" 표식**(눈 아이콘 + 텍스트)이
  항상 보여 "이건 원래 보기 전용"임을 알린다. 프레즌스(상대 커서 + 이름, 헤더의 "함께 보는 사람")는 **노트에만** 있다.

### 4.4 알림 모아보기 (알림 센터)

- 코멘트 알림(4.3)이 쌓이는 곳이 필요하다 — 지금 사이드바 하단에 **휴지통 패널과 동일한
  패턴**이 이미 있다(`src/sidebar/Sidebar.tsx:779` `sb-foot-btn` + `sb-dot-badge`,
  `useTrash`/`openTrash()` 구조). 알림도 같은 자리·같은 모양으로 만든다 —
  `UI-DESIGN-PRINCIPLES.md`의 "같은 역할의 요소는 같은 모양" 원칙.
  - 사이드바 맨 아래에 종 모양 아이콘 버튼 추가(휴지통 버튼 옆). 읽지 않은 알림이 있으면
    `sb-dot-badge`로 표시.
    → 구현: 점이 아니라 **숫자 뱃지**(`sb-count-badge`, 10개 이상은 "9+" — 1개와 9개는 다른 정보). 종 버튼은 공유 폴더가
    있거나 받은 알림이 남아 있을 때만 보인다(공유를 안 쓰는 사용자의 화면은 그대로).
  - 클릭하면 휴지통과 같은 방식의 하단/오버레이 패널이 열려 알림 목록을 최신순으로 보여준다.
    → 구현: 관리형 오버레이 스택(ADR 0018)에 편입. 패널을 열기만 해서는 읽음 처리되지 않는다.
  - 각 알림 항목: 작성자·코멘트 미리보기·대상(어느 노트/노드/요소인지)·시각. 클릭하면 그
    파일을 열고 해당 노드/요소로 스크롤+선택(보드의 `revealNode`류 로직 재사용) 하면서
    자동으로 읽음 처리.
  - "모두 읽음" 일괄 처리 버튼.
- **읽음/안읽음은 참가자 로컬 상태**다 — 코멘트 자체(4.3)는 공유 폴더 참가자 전원에게
  동일하게 보이지만, "내가 이걸 읽었는지"는 사람마다 다르므로 서버로 동기화하지 않고
  각자 로컬에 저장한다(신설 `notificationStore`, 워크스페이스 메타 저장 패턴 — 기존
  `meta:*` IPC 채널과 유사하게 로컬 파일/설정에 영속화).
  → 구현: `notifications:load`/`notifications:save` IPC(2개) → `userData/notifications.json`(워크스페이스가 아니라 userData,
  최근 500건, 방별 기준선 포함). 항목별 읽음 토글과 "모두 읽음" 모두 제공, 항목 클릭은 파일 열기 + 노드/요소 선택 +
  스레드 열기 + 읽음.
- 알림 종류는 1차로 "코멘트"만. 향후 "누가 노트에 참가했다/나갔다" 같은 시스템 알림으로
  확장 가능하도록 `type` 필드를 열어둔다(YAGNI — 지금은 `type: 'comment'` 하나만 구현).

### 4.5 초대 코드 · 권한

- 코드는 **TTL(예: 10분)이 있는 1회용 티켓** — 참가 시점에 참가자별 영구 토큰으로 교체된다.
  폴더 소유자는 참가자 목록을 보고 개별 강퇴(토큰 revoke)할 수 있어야 한다.
  → 구현: 8자 코드, 10분 TTL, 1회용. 참가자 목록의 "내보내기"가 강퇴이며 서버가 라이브 연결을 즉시 끊는다(close 4403).
  **발급한 코드를 취소하는 기능은 없다**(만료·사용 전까지 유효 — 공유 해제 후에도 최대 10분). 소유자 "공유 해제" = 남은
  참가자를 모두 내보낸 뒤 로컬 정리(서버에 방 삭제 기능 없음). 참가자는 "나가기".
- 권한은 3단계: **소유자(admin, 모든 편집+강퇴)** / **참가자(자기 노트 공동편집 + 코멘트,
  맵·보드는 뷰만)** — 사용자 요구사항엔 없지만 향후 "이 노트도 편집 못 하게" 같은 세분화
  요청이 나올 걸 대비해 참가자 단위 권한 필드는 확장 가능하게 설계.
  → 구현: **역할은 소유자/참가자 2종**이다(위 "3단계"는 실제로 둘이었다). 세분화 권한 필드는 만들지 않았다(§5).

### 4.6 새 도메인

- `src/share/` 신설 — exec-plan 선행 필요(`architecture.md` 규칙). `shareStore`(참가자 목록,
  연결 상태, 권한)는 `store/`에 추가하고 note/canvas/board는 이 store를 통해서만 연결.
  → 구현: `src/share/` + `store/shareStore`·`commentStore`·`notificationStore`·`readOnlyGuard`, `electron/share.ts`·`notifications.ts`,
  `server/`. 모듈 책임·IPC 그룹(`share:*` 15개 + `notifications:*` 2개)·데이터 플로우는 `ARCHITECTURE.md`.
- 신규 의존성: `yjs`, `@hocuspocus/*`(서버·클라이언트), `@tiptap/extension-collaboration`,
  `y-protocols`(awareness) — 라이선스·번들 크기 검토 후 **인간 승인 필요**(`AGENTS.md`).
- 신규 macOS/운영 부담: 지금까지 "서버 없음"이던 프로젝트가 처음으로 **상시 운영 서버**를
  갖게 된다(호스팅 비용, 가동시간 보장, 보안 패치 — 일회성 빌드가 아니라 지속적 운영 부담).
  이건 기능 하나 추가가 아니라 **운영 모델 자체의 변화**라 별도로 짚어둔다.

  전송 구간 자체의 무지(zero-knowledge)는 후속 검토.
- 알림 필터/카테고리 탭("코멘트만 보기" 등) — 알림 종류가 코멘트 하나뿐이라 불필요, 종류가
  늘어나면 재검토.
- 읽음 상태의 다중 기기 간 동기화 — 이 앱은 기기당 로컬 상태 기준으로 시작(기존 앱도 다중
  기기 동시 사용을 전제하지 않음).
- (구현 중 추가로 뺀 것) 맵·보드의 뷰어 프레즌스, 노트 코멘트의 텍스트 범위 앵커(노트 전체 단위만), 공유 노트·보드의 이미지 공유,
  발급한 초대 코드의 취소, 서버 측 코멘트 작성자 검증.
