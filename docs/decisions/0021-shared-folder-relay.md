# 0021. 공유 폴더: 자체 호스팅 릴레이 서버 도입과 "서버 없음" 불변 조건의 재정의

날짜: 2026-09-21 · 상태: 채택 (2026-09-21 사용자 승인 — "모두 실행해")

## 맥락

여러 사용자가 초대 코드로 폴더를 공유하고, 노트는 실시간 공동편집, 마인드맵·보드는 소유자만
편집하고 나머지는 보기+코멘트만 하는 "공유 폴더" 기능을 만들려 한다(명세:
`docs/product/specs/2026-09-21-shared-folder-collab.md`).

이 기능은 최소한 (1) 초대 코드 발급·검증, (2) 참가자 간 실시간 메시지 전달을 위한 **상시 운영
서버**가 필요하다. 그런데 `AGENTS.md`의 최우선 불변 조건은 "사용자 데이터(`.mind`, `.md`)는
절대 서버로 전송하지 않는다"이고, 결정 0020은 같은 이유로 보드의 실시간 협업을 범위에서
제외했다. 즉 이 기능은 프로젝트 정체성의 한 축을 건드린다.

검토한 선택지:

| 선택지 | 판단 |
|---|---|
| Google Docs식 OT | 서버가 편집 순서를 중재하며 콘텐츠를 알아야 한다. 기각. |
| Liveblocks 등 관리형 CRDT | 문서가 제3자 회사 서버를 거친다. 기각. |
| Obsidian Sync식 파일 동기화(동시편집 없음) | 철학은 가장 가깝지만 "노트 동시편집" 요구를 못 채운다. 기각. |
| 순수 P2P(WebRTC) | 코드 입력 참가는 시그널링 서버가 어차피 필요하고, NAT·오프라인 도착 처리가 불안정. 기각. |
| **Yjs CRDT + 자체 호스팅 Hocuspocus 릴레이** | 현재 에디터(Tiptap)와 통합 경로가 잘 닦여 있고, 서버 코드를 우리가 통제한다. **채택안.** |

## 결정

1. **불변 조건 재정의.** "사용자 데이터는 절대 서버로 전송하지 않는다"를 다음으로 바꾼다:
   > 사용자 파일은 로컬이 원본이다. 사용자가 명시적으로 **공유 폴더로 지정한 폴더**의 내용만,
   > **우리가 운영하는 릴레이 서버**를 통해 참가자에게 전달되며, 릴레이는 콘텐츠를 디스크에
   > 영속 저장하지 않는다. 공유하지 않은 폴더·파일은 어떤 경우에도 전송되지 않는다(폴더 단위
   > opt-in).
2. **릴레이 서버는 콘텐츠를 저장하지 않는다.** 접속 중인 클라이언트 사이의 Yjs 업데이트를
   메모리에서 중계하고, 방(room)에 접속자가 0이 되면 메모리 상태를 폐기한다. 서버가 영속
   저장하는 것은 **메타데이터뿐**이다: 방 id, 소유자·참가자 토큰의 해시, 표시 이름, 강퇴 목록,
   **폴더 이름(`folder_name`)**, 마지막 활동 시각. 폴더 이름은 소유자가 지정한 자유 문자열이라
   개인정보 성격이 있다(소유자가 오프라인이어도 참가자가 폴더 이름을 알아야 해서 저장한다 — 로그에는 남기지 않는다).
   소유자는 방 삭제 API(`DELETE /rooms/:roomId`)로 이 메타데이터를 통째로 지울 수 있고, 서버는 마지막 활동 후
   `ROOM_TTL_DAYS`(기본 90일)가 지난 방을 스스로 정리한다.
3. **노트만 실시간 공동편집(Yjs).** 마인드맵·보드는 CRDT를 쓰지 않는다 — 소유자 클라이언트가
   유일한 쓰기 주체이고, 릴레이는 "파일이 바뀌었다" 이벤트만 전달한다. 결정 0020의 "보드
   실시간 협업 제외"는 유지된다(참가자는 보기+코멘트만).
4. **각 참가자의 로컬 `.md`가 계속 원본이다.** 공유 노트의 Y.Doc 상태는 각자 로컬에 숨김
   사이드카 파일로 저장하고(공유 폴더 안의 숨김 폴더 `.mindshare/` 아래 노트 id 기반 파일 —
   결정 0010의 숨김 폴더 관례와 같은 사고), `.md`는 여기서 디바운스로 파생한다. 서버가 상태를 폐기해도 클라이언트가 재접속 시 병합할 수 있는 이유다.
5. **신원은 계정이 아니라 토큰.** 초대 코드는 TTL이 있는 1회용 티켓이고, 참가 시 참가자별
   영구 토큰으로 교체된다(macOS Keychain/`safeStorage`에 보관 — AI 키와 같은 방식). 소유자는
   참가자 토큰을 개별 revoke할 수 있다.
6. **네트워크 경계.** WebSocket 클라이언트는 Yjs 프로바이더가 에디터와 같은 프로세스에 있어야
   해서 렌더러에서 동작한다. 이를 위해 렌더러 CSP `connect-src`를 릴레이 origin 하나로 제한해
   추가한다(현재 CSP 없음 — 신설). 릴레이 URL은 `share:*` IPC를 통해 main이 검증·제공한다.

## 결과

- 좋은 점: 노트 동시편집이 검증된 라이브러리 조합으로 가능. 서버가 콘텐츠를 모르는 정책을
  구조적으로 강제할 수 있다(영속 저장 코드 자체가 없음). 공유하지 않는 사용자는 아무 변화가
  없다.
- **나쁜 점 / 비용**:
  - 프로젝트 최초의 **상시 운영 서버**: 호스팅 비용, 가동시간, 보안 패치가 지속 부담이 된다.
  - `AGENTS.md`·`FEATURE-INVENTORY.md`("실시간 협업 없음" 한계)·결정 0020 본문의 관련 문구를
    이 결정에 맞춰 갱신해야 한다(채택 시).
  - `NoteEditor.tsx`가 "타이핑마다 ProseMirror→마크다운 변환"인 현재 구조에서 "Y.Doc이 진실,
    마크다운은 파생"으로 바뀌어야 한다. 공유 폴더 안의 노트에만 적용하고 일반 노트 경로는
    그대로 두어 회귀 범위를 제한한다.
  - **가장 큰 기술 리스크**: 두 클라이언트가 같은 `.md`에서 각자 Y.Doc을 시드하면 병합 시
    내용이 중복된다. 사이드카 상태 보존과 "방에 처음 들어온 쪽만 시드, 이후 참가자는 원격
    상태를 채택" 규칙으로 완화할 계획이며, 구현 전에 스파이크로 검증한다(exec-plan 단계 2).
  - **가용성 한계**: 서버가 콘텐츠를 저장하지 않으므로, 신규 참가자는 다른 참가자가 1명 이상 온라인일
    때만 기존 내용을 받는다(모두 오프라인이면 각자 로컬 복제본만 존재). 이미 참가한 사람은 로컬
    복제본으로 계속 작업하고 재접속 시 병합된다. 항상 켜져 있는 저장이 필요해지면 서버 측 암호화
    영속화를 이 결정의 개정으로 검토한다.
  - 외부 에디터로 `.md`를 직접 고친 경우(사이드카와 불일치)의 처리 정책이 필요하다.
- 신규 의존성(인간 승인 필요): `yjs`, `y-protocols`, `@hocuspocus/provider`,
  `@tiptap/extension-collaboration`(+ 커서 확장), 서버 측 `@hocuspocus/server`.

## 신뢰 모델

공유 폴더는 "서로 아는 사람끼리 초대 코드로 모이는 협업"을 전제로 하며, 참가자 사이의 권한은 다음처럼 비대칭이다.

- **소유자 권위는 맵·보드 항목(`file:*`)에만 적용된다.** 서버가 소유자만 쓰기를 허용하고 참가자는 읽기 전용으로 강제한다.
- **`manifest`와 `comments`는 모든 참가자가 쓸 수 있다.** manifest는 모든 참가자가 쓸 수 있어 참가자가 노트 항목 삭제로 다른
  참가자의 로컬 복사본을 휴지통으로 보낼 수 있다 — 복구 가능(파일이 지워지지 않고 앱 휴지통으로 간다). 코멘트 작성자도 서버가
  검증하지 못한다. 악의적 참가자를 막는 모델이 아니라, 신뢰하는 사람 사이에서 실수와 외부인을 막는 모델이다.
- **소유자는 언제든** 참가자를 내보내거나(토큰 폐기 + 라이브 연결 종료) 방 전체를 삭제할 수 있다(`DELETE /rooms/:roomId` — 방·참가자·
  미사용 초대·폴더 이름 삭제, 그 방의 모든 소켓을 close 4403 `room_deleted`로 종료).
- 서버는 자원 고갈에 대비한 한도(인증 전 프레임 상한·문서·방 메모리 예산·연결 수·메시지 속도·`/join` 브루트포스 백오프)를 둔다.
  수치와 근거는 `docs/operations/relay-server.md`.

## 호스팅: Railway

릴레이는 Railway에 배포한다(같은 계정의 다른 프로젝트 — `babyscience-landing-web`,
`marketing-recipe` 등이 이미 Railway 사용). 그 프로젝트들의 관례를 따른다: Nixpacks 자동 감지
(`npm start`), 서버 코드는 앱과 의존성을 완전히 분리한 독립 디렉터리(`server/`, babyscience의
`app-api/`와 같은 패턴), SQLite는 Railway 볼륨(`/data`, `DB_PATH` 환경변수) — marketing-recipe와 동일.
이 저장소의 원격은 다른 GitHub 계정(SteveKim0513)이라 GitHub 자동 배포에 기대지 않고
`railway up`(CLI)으로 `server/`를 배포한다.

Railway 운영 제약(설계에 반영):
- **인스턴스 1개.** 방 상태가 메모리에 있어 수평 확장 시 같은 방이 갈라진다. 확장은 Redis 확장 등을 그때 재검토.
- **재배포 시 연결 끊김 + 볼륨 때문에 무중단 배포 불가.** 클라이언트 자동 재접속 + 로컬 Y.Doc 사이드카로 데이터 손실 없음.
- 서버 로그에 문서 내용·토큰을 절대 남기지 않는다(서버 테스트로 강제).
- Railway는 TLS를 자기 엣지에서 종단하므로 기술적으로 호스팅 업체 인프라는 평문 트래픽을 볼 수 있다.
  결정 1의 "콘텐츠를 저장하지 않는다"는 우리 애플리케이션 코드의 보증이지 호스팅 업체에 대한 보증이
  아니다. v1에서는 수용하고, 종단간 암호화는 후속 과제로 유지한다.
