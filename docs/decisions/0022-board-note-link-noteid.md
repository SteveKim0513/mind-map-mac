# 0022. 보드의 노트 링크는 노트 id로 건다 — 공유 폴더 참가자에게도 칩이 작동한다

날짜: 2026-09-21 · 상태: 채택 (2026-09-21 사용자 승인 — 공유 검토 라운드의 "공유 사본 노트 링크 칩 소실" 항목에서 옵션 C "노트 id로 링크" 선택)

## 맥락

보드의 스티키·이미지는 노트 파일로 가는 링크 칩을 가질 수 있다(`BoardStickyElement.noteLink` /
`BoardImageElement.noteLink`, 타입 `BoardNoteRef`). 지금까지 이 링크는 `{ notePath, title }`이고
`notePath`는 **링크를 만든 Mac의 절대 경로**다. 이 방식에는 두 가지 문제가 있다.

1. **노트 이름 변경·이동에 깨진다.** 경로가 진실이라, 노트를 다른 이름·폴더로 옮기면 칩이 조용히 죽는다.
   (노드↔노트 링크는 노트 프론트매터의 안정 id를 쓰는데 보드→노트 링크만 경로를 쓴다.)
2. **공유 폴더(ADR 0021)에서 참가자에게 쓸 수 없다.** 소유자의 절대 경로는 다른 기기에서 무의미하고,
   원격이 채운 경로가 `readFile`·편집·저장 경로가 되면 임의 파일을 열 수 있어 위험하다. 그래서 공유 사본에서는
   `noteLink`를 통째로 제거해 왔다(`io/sharedFile.ts`·`io/sharedValidate.ts`) — 결과적으로 참가자의 보드에서
   노트 링크 칩이 사라졌다(공유 검토 라운드에서 발견, 인간 판단 항목).

공유 폴더 안 노트는 참가자에게도 같은 프론트매터 `id`를 가진 파일로 물질화된다(ADR 0021 6a). 즉 **노트 id는
두 기기에서 같은 노트를 가리키는 공통 키**다.

## 결정

`BoardNoteRef`에 **선택 필드 `noteId?: string`**(노트 프론트매터 `id`)을 추가하고, **`BoardDoc.version`은 1로
유지**한다(ADR 0012 선례 — 순가산 선택 필드, 옛 앱은 모르는 필드를 무시하고 JSON 왕복에서 보존). `notePath`는
로컬 폴백으로 남기되 공유 사본에서는 `optional`이다(`notePath?: string`).

- **링크 생성**: 노트 링크 피커가 선택한 노트의 id를 함께 저장한다(`boardNoteRef`). 새로 만들어 연결할 때도 그 노트의 id.
- **칩 클릭(모든 사용자)**: ① `noteId` → **로컬 워크스페이스 노트 인덱스**에서 현재 경로(이름 변경·이동에 강함) ② 못 찾으면 옛
  `notePath` ③ id가 있는데 둘 다 실패하면 재스캔 1회 후 id 재시도 ④ 그래도 실패면 토스트(조용한 실패 금지).
  열기 직전 `isPathInsideRoot`(워크스페이스 안 `.md`)는 id로 해석한 경로에도 그대로 적용한다.
- **옛 보드(noteId 없음)**: 동작 그대로. 기존 파일을 자동 수정·마이그레이션하지 않는다(파일 바이트 불변). 옛 링크는 사용자가 다시
  링크를 만들 때, 또는 공유 발행 시점(사본에서만)에 id로 해석된다.
- **공유 발행(소유자 → 사본)**: 소유자 기기에서 링크 대상 노트 id를 얻는다 — `noteId`가 있으면 그것, 없으면 `notePath`(절대 경로)를
  공유 노트 매핑으로 해석. 그 노트가 **공유 폴더 안 노트(= manifest에 있어 참가자에게 복제되는 노트)일 때만** 사본에
  `{ noteId, title }`를 남기고 **`notePath`는 사본에서 항상 제거**한다. 폴더 밖 노트·해석 실패면 사본에서 `noteLink`를 제거한다
  (현행과 동일). **소유자의 실제 파일은 수정하지 않는다** — 사본만 정제한다. 소유자 기기에서만 알 수 있는 정보(절대 경로 ↔ id,
  manifest 소속)는 `io/`가 store·도메인을 import하지 않도록 **해석기(`resolveNoteLink`)로 주입**한다(`share/rooms.ts`가
  ReplicaManager·manifest로 만든다). 공유 노트 목록이 바뀌면(노트가 나중에 공유·삭제·이동) 링크가 있는 보드만 다시 정제·발행한다.
- **참가자 수신·클릭**: 사본의 `{ noteId, title }`(경로 없음)을 클릭하면 **로컬 노트 인덱스에서 id로** 경로를 찾아 연다. 아직
  동기화 전이거나 삭제됐으면 "노트를 찾지 못했어요. 아직 동기화 중이거나 삭제됐을 수 있어요" 토스트. 읽기 전용 미러 보드에서
  칩으로 노트를 여는 것은 문서를 바꾸지 않으므로 허용한다.
- **수신 재검증**: `noteId`가 안전한 id 형식(`isSafeDocId`)이 아니면 링크 제거, `notePath`는 어떤 경우에도(상대 경로 포함) 제거한다 —
  공유 사본은 더 이상 경로 기반 링크를 받지 않는다. 사본의 `title`은 제어문자가 없는 512자 이내 문자열만 남긴다.
- 로드 경계(`io/boardFormat.parseBoard`)는 `noteId`가 노트 id 형식이 아니면 그 값만 버린다(`notePath` 폴백은 유지).

reminder 불변 조건, `MindMapDoc.version`·`BoardDoc.version`, 노드/노트 id 발급은 바뀌지 않는다. 맵 노드의 `nodeLink`
(mapId/nodeId)·`mapPath` 처리는 이번 범위 밖이다.

## 결과 — 트레이드오프, 다시 볼 조건

- 장점: 노트 이름 변경·이동에 링크가 깨지지 않는다(소유자에게도 이득). 공유 폴더 참가자에게도 칩이 작동한다. 경로가 아니라 id로만
  해석하므로 참가자 기기에서 임의 경로를 열 수 없다(보안 경계 강화 — 원격이 채운 경로 문자열은 신뢰하지 않는다).
- 트레이드오프: 옛 보드의 링크는 다시 만들기 전까지 경로 기반이라 이름 변경에 여전히 취약하다(자동 마이그레이션을 하지 않기로
  했으므로). 공유 사본은 링크 대상이 **공유 폴더 안 노트**일 때만 칩이 남고, 대상 노트가 아직 manifest에 오르기 전에 발행되면
  잠깐 칩이 없다가 노트가 공유되는 즉시 다시 발행된다. 프론트매터 id가 없는 노트는 링크 피커가 저장한 id가 파일 안의 id와
  다를 수 있어(파일에 id가 스탬프되기 전) 그때는 경로 폴백·공유 시점 경로 해석에 의존한다.
- 다시 볼 조건: 노트 id 규칙(`isSafeDocId`) 변경, 노트 id 자동 스탬프 시점 변경, 보드 이미지·맵 링크(`nodeLink`)도 같은 방식으로
  공유하고 싶을 때. 구버전 앱은 `noteId`를 무시하고 `notePath`로 동작하므로 상호 안전하다(공유 사본에는 경로가 없으므로 구버전
  참가자에게는 칩이 없다 — 이전과 같다).

## 대안

- (A) 공유 사본에서 노트 링크를 계속 제거 — 안전하지만 참가자 보드에서 칩이 영영 사라진다. 기각(사용자 선택 C).
- (B) 상대 경로를 공유 폴더 기준으로 저장 — 이름 변경·이동에 여전히 깨지고, 참가자 폴더 안 로컬 파일명이 달라질 수 있다
  (충돌 사본 접미사 등). 경로 문자열을 신뢰해야 하는 보안 부담도 남는다. 기각.
- (C, 채택) 노트 id — 이름 변경에 강하고 두 기기에 같은 키가 있다.
- (D) `BoardDoc.version` 2 + 자동 마이그레이션 — 실행할 변환이 없고 사용자 파일을 조용히 고쳐 쓰는 위험만 생긴다(0012와 같은
  판단). 기각.
