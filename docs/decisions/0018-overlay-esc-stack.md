# 0018. 관리형 오버레이 스택 — 닫기/Esc의 한 단계 복귀
날짜: 2026-07-19
상태: accepted

## 컨텍스트
관리형 오버레이 9개(설정·사용 안내·최근 수정·즐겨찾기·휴지통·노트 템플릿·이전 버전·집중 기록·업데이트 내역)는 독립 boolean으로 열리고, 각자 `window.addEventListener('keydown', …, true)`로 Esc를 처리했다. 이 구조가 만든 경로 소실 문제(감사로 확인):

- **설정 → "최근 수정"**: 겹치면 z-order(정적 DOM 렌더 순서, 전부 z-88)상 RecentView가 아래에 깔려 클릭을 못 받으므로 `closeSettings()`로 설정을 닫고 열었다 → Esc로 설정에 못 돌아온다.
- **설정 → "사용 안내"**: 두 오버레이의 window 캡처 리스너가 동시 발화해 Esc 1회에 둘 다 닫혔다. `stopPropagation()`은 같은 타깃(window)의 다른 리스너를 막지 못한다.
- **⌘K로 오버레이 위에 다른 오버레이 열기**: 나중에 연 것이 DOM 순서에 따라 아래에 깔릴 수 있었다.

## 결정
`uiStore`에 **열린 순서 스택** `overlayStack: OverlayId[]`을 도입한다 (boolean은 유지, 각 `open*`/`close*` 액션 안에서 동기 갱신 — 파생 상태 전환은 하지 않는다).

1. **한 단계 복귀**: 닫기/Esc/배경 클릭은 최상단 레이어 하나만 닫는다. 공용 훅 `useOverlayEsc(id, onEsc)`가 스택 최상단 === id일 때만 콜백을 실행 — store를 직접 조회하므로 리스너 등록 순서와 무관하게 결정적이다. 오버레이 내부 단계(설정 서브페이지, 집중 기록의 펼침→필터)는 콜백 안에서 먼저 복귀한다.
2. **z-order = 스택 순서**: 백드롭 z-index를 `88 + 스택 위치`로 동적 적용 — 나중에 연 오버레이가 항상 위. 팔레트류(⌘P/⌘K/전체 검색)는 스택 밖이며 z-100으로 항상 관리형 위(스택 최대 96). 팔레트가 열려 있으면 관리형 Esc 훅은 무시한다 — 팔레트 자신이 닫히는 것이 그 한 단계다.
3. **목적 달성 시 전체 해소**: 파일 열기 등 화면을 떠나는 액션은 `closeAllOverlays()`로 스택 전체를 해소한다 (최근 수정·즐겨찾기의 "열기").

### WhatsNew 카드 예외
업데이트 직후 1회성 WhatsNew 카드는 스택 밖이다(z-98). "전체 내역" 클릭 시 카드를 닫고 업데이트 내역을 여는 현행 동작은 유지 — 카드 내용이 전체 내역의 부분집합이므로 "뒤로 돌아갈 이유가 없는" 목적 달성 이동으로 판정했다.

## 결과
- 장점: 설정 → 최근 수정/사용 안내에서 Esc가 설정으로 복귀. 겹침 순서가 열린 순서와 항상 일치. 오버레이 간 전환 시 아래 레이어를 닫는 우회(z-order 회피)가 불필요해졌다.
- 단점: boolean + 스택 이중 상태 — store 액션 밖에서 boolean을 직접 만지면 어긋난다(액션 경유가 계약). 스택 밖 오버레이(UpdateStatus 팝업 등 transient)는 여전히 자체 Esc 처리라 최상단 관리형 오버레이와 동시 발화할 수 있다.

## 대안
- **boolean을 스택 파생 상태로 전면 전환**: 이중 상태는 없어지지만 9개 오버레이의 모든 구독 지점을 갈아야 해 회귀 반경이 크다. 스택 갱신을 액션 안으로 한정하는 것으로 위험을 통제하고 기각.
- **DOM 렌더 순서 재배열로 z-order 해결**: 열린 순서는 런타임 정보라 정적 JSX 순서로는 표현 불가. 기각.
- **Esc 리스너를 App 단일 지점으로 통합**: 오버레이 내부 단계 복귀(설정 서브페이지 등)까지 App이 알아야 해 결합이 커진다. 훅 + 스택 조회로 동등한 결정성을 얻으므로 기각.
